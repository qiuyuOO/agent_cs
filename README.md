# CS2 Demo × 音乐 自动剪辑 Agent

用 **音乐情绪** 驱动 **CS2 demo 战术回放** 的自动剪辑：输入一个 `.dem` 文件 + 一首歌，
输出一条音画同步的成片。

画面不是游戏内录屏，而是从 demo 的逐 tick 坐标直接渲染的 **2D 雷达动画**
（玩家圆点、移动拖尾、击杀特效、烟雾/燃烧/闪光、实时比分 HUD）。
好处是**全自动、可复现、可离线批处理**，不需要开游戏、不需要 HLAE、不需要人工录制。

## 快速开始

```bash
# 0) 图形界面 (推荐): 开浏览器点几下就出片
E:\agent_cs\.venv\Scripts\python.exe -m cs2clipper.webapp
#    默认 http://127.0.0.1:8760/ —— 出片 / 时间轴 / 偏好画像 / 历史记录

# 1) 命令行: 用工作区内置的虚拟环境 (已装好全部依赖)
E:\agent_cs\.venv\Scripts\python.exe -m cs2clipper.pipeline ^
    --music 你的歌.mp3 ^
    --demo  D:\path\to\match.dem ^
    --out   E:\agent_cs\out\myrun

# 2) 没有音乐素材时, 先跑合成测试曲验证全链路
E:\agent_cs\.venv\Scripts\python.exe -m cs2clipper.pipeline --demo-track

# 3) 跳过 LLM, 用确定性编排 (离线/省钱)
E:\agent_cs\.venv\Scripts\python.exe -m cs2clipper.pipeline --music 你的歌.mp3 --no-llm
```

成片在 `--out` 目录下的 `final.mp4`，中间产物：

| 文件 | 内容 |
|---|---|
| `final.mp4` | 成片 (1024×1024, 30fps, 带音轨) |
| `edl.json` | **剪辑决策清单** —— 每段用了哪条素材、源 tick 区间、倍速、理由 |
| `music_analysis.json` | 音乐结构：BPM、拍点、段落、每段的激烈度/亮度 |
| `demo_analysis.json` | demo 结构：回合表 + 40 条亮点素材及其评分与标签 |
| `clips/` | 每段独立的中间视频（方便单独重渲） |

命令行参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--music` | 必填 | 音乐文件 |
| `--demo` | 项目内置示例 | CS2 demo 路径 |
| `--out` | `out/<歌名>` | 输出目录 |
| `--aspect` | `wide` | 画幅：`wide`=1920×1080（B站/YouTube）、`tall`=1080×1920（抖音/Shorts）、`square`=1024×1024 |
| `--fps` | 30 | 帧率 |
| `--max-clips` | 22 | 剪辑段数上限 |
| `--max-cards` | 40 | 亮点素材池大小 |
| `--no-llm` | 关 | 不用 LLM，走确定性编排 |
| `--demo-track` | 关 | 生成合成测试曲来跑通全链路 |

### 画幅与布局

三种画幅共用同一套渲染器，只换 `radar.Layout`：

| 画幅 | 画布 | 地图区 | 信息面板 |
|---|---|---|---|
| `square` | 1024×1024 | 占满 | 无（上下压条 HUD） |
| `wide` | 1920×1080 | 1024×1024 靠左 | 右侧竖栏（回合/比分/主角/击杀/标签） |
| `tall` | 1080×1920 | 1024×1024 在上 | 下方横栏 |

面板不是"黑边"——是刻意留白的真实信息区，所以直接推到平台不会像加黑边的正方形视频。

```bash
# 抖音竖屏
python -m cs2clipper.pipeline --music 歌.mp3 --aspect tall --out out/douyin
```

## 架构：五段流水线

用 LangGraph 编排。`analyze_music` 与 `analyze_demo` **并行**执行，之后汇合到 `plan`。

```
        ┌──────────────┐
        │ analyze_music│──┐
        └──────────────┘  │   ┌──────┐   ┌───────────────┐   ┌────────┐   ┌─────────┐
                          ├──▶│ plan │──▶│ save_artifacts│──▶│ render │──▶│ compose │──▶ END
        ┌──────────────┐  │   └──────┘   └───────────────┘   └────────┘   └─────────┘
        │ analyze_demo │──┘
        └──────────────┘
```

| 阶段 | 模块 | 做什么 |
|---|---|---|
| 1 | `music.py` | BPM / 拍点 / RMS 能量 / 低频占比 / 频谱质心 → 自动分段 + 情绪标注 |
| 2 | `demo.py` | 解析 demo，按主角聚合连杀，产出带**确定性评分**的亮点卡片 |
| 3 | `planner.py` | LLM 编排（或确定性兜底）→ 展开成精确到 tick 的 **EDL** |
| 4 | `radar.py` + `mapview.py` | 逐帧渲染雷达画面 (PIL)，含轨迹/击杀/道具/HUD |
| 5 | `compose.py` | ffmpeg 编码每段 + 拼接 + 统一铺音乐 |

### 关键设计决策

**1. LLM 只做选择，不做算术。**
LLM 的职责是"哪段音乐配哪些素材、什么顺序"，输出高层 JSON；
时间轴、tick 区间、总时长全部由代码计算与校验（`_expand` + `validate_edl`）。
因此即使 LLM 把时长写得离谱，成片也不会错乱，最坏只是排序不理想。

**2. 时长由音乐决定，素材去适配音乐。**
段落时长 → 镜头条数（`_clips_for_span`）→ 精确分配的每段时长（`_allocate_durations`），
再用倍速与 tick 裁剪把素材塞进这个窗口。
这保证了**时间轴首尾相接、精确铺满**，不会出现十几秒的空画面（这个 bug 在开发中真实出现过）。

**3. 情绪用两个正交轴，不硬凑"正能量"。**
- `arousal`（激烈度）= RMS 能量 + 低频冲击 + 节拍密度 → 决定**剪辑密度与镜头时长**
- `brightness`（频谱亮度）= 频谱质心 + 滚降 → 决定**画面色彩与特效强度**

底鼓重的 drop 段是"高激烈度 + 暗"，这是正确的物理事实，不强行映射成"负面情绪"。
段落用途主要由结构标签（`intro/build/chorus/drop/breakdown/outro`）决定。

**4. 音乐只在最后铺一次。**
早期实现给每个片段单独裁一段音乐并做 `atempo` 变速，结果：慢放镜头触发 atempo 的
0.5~100 下限直接报错、每段各自重采样导致接缝相位对不齐、段间空隙变成静音。
现在视频段先无音轨拼接，最后统一混入整首歌并做尾部淡出 —— 音画天然同步。

**5. 雷达底图不依赖外部素材。**
`awpy` 官方的地图资源 (`awpycs.com/<build>/maps.zip`) 当前返回 404，
所以没有走 Valve 雷达贴图路线，而是**按 demo 实际活动范围自适应取景** +
用 PIL 画网格与区域标签（点位名来自 demo 的 `place` 列，如 `LongA`/`BombsiteB`）。
无需任何外部素材，任意地图都能工作。

**6. 两个"补齐"机制保证成片不断。**
这两个都是开发中真实踩到的坑：

- **补结尾**（`_top_up_tail`）：LLM 常常只排到音乐的三分之二就收工
  （实测 72 秒的歌只排 58 秒）。代码会自动从未使用的素材里继续排，
  直到铺满音乐。
- **补段长**（`compose.finalize_clip`）：渲染器按 `speed` 生成帧数，
  慢放镜头（speed < 1）生成的帧比时间窗少，导致每段都比声明短一点，
  累积起来视频轨比音频轨短几秒、结尾黑屏。现在用 ffmpeg `tpad`
  克隆最后一帧补齐差额，实测每段偏差 ≤ 0.010s。

## 用户偏好与运行记录（本地 SQLite）

出片涉及十几个参数，每次手打一遍不现实。偏好与历史记录持久化在
**`data/clipper.db`**（首次使用自动建表，无需初始化）。

```
data/clipper.db
├── preferences   16 项可配置偏好 (键值对 + 更新时间)
├── runs          每次出片的记录 (输入/设置/产物/耗时)
└── clips         每次运行里逐段剪辑的明细
```

### 用起来是什么样

```bash
# 存偏好（可一次写多组）
python -m cs2clipper.pipeline --set aspect tall max_clips 14 use_llm false

# 之后直接出片，已存的偏好会自动生效
python -m cs2clipper.pipeline --music 歌.mp3 --demo 局.dem

# 查看 / 清理
python -m cs2clipper.pipeline --show-prefs
python -m cs2clipper.pipeline --show-runs          # 最近 10 次出片
python -m cs2clipper.pipeline --show-stats         # 库大小/成片总量/平均耗时
python -m cs2clipper.pipeline --reset-prefs aspect  # 清某一项
python -m cs2clipper.pipeline --reset-prefs         # 清全部

# 本次临时忽略已存偏好 / 不留记录
python -m cs2clipper.pipeline --music 歌.mp3 --no-prefs
python -m cs2clipper.pipeline --music 歌.mp3 --no-record
```

### 可配置的 16 项

| 分类 | 偏好 |
|---|---|
| 输出 | `aspect` / `fps` / `out_root` |
| 编排 | `use_llm` / **`pacing`** / `max_clips` / `max_cards` / `min_score` |
| 镜头 | `zoom_base` / `zoom_per_arousal` |
| 特效 | `fade_in` / `fade_out` / `shake_px` / `trail_blur` / `vignette` / `show_places` / `show_hud` |

### 偏好会进提示词（不只是代码里事后夹取）

LLM 编排时，偏好会作为 `user_preferences` 段注入提示词：

```json
{
  "max_clips": 10,
  "pacing": "cinematic",
  "pacing_meaning": "电影感：镜头更长、留白更多，让每个画面有余韵",
  "clip_duration_range": {
    "drop": [1.8, 6.1],  "intro": [3.9, 12.2],
    "verse": [1.8, 8.1], "build": [3.9, 12.2], "outro": [3.9, 12.2]
  },
  "notes": ["max_clips 是总数上限，不是每段上限",
            "单条时长必须落在对应段落标签的区间内"],
  "visual_style": ["不显示 HUD 与比分", "关闭击杀震屏"]
}
```

为什么必须进提示词：偏好如果只在代码里事后夹取，LLM 会按自己的风格排出一个
"超限方案"再被硬裁 —— 结果既不是它想排的，也不完全符合用户偏好。提前把节奏、
段数上限、单条时长区间告诉它，它才能一次排对。

两个关键设计：

1. **区间来自与展开器同一个函数**（`_segment_limits(arousal, rel_energy, pacing)`）。
   提示词里报的数字就是代码实际会夹取的范围，两边不会打架。
2. **区间向外取整**（下界向下、上界向上）。最初用 `round()`，提示词报的下界
   `1.1` 比实际可夹取的 `1.05` 更窄，LLM 严格照提示词排反而会被判越界。

`pacing` 的三种取值：

| 取值 | 单条时长倍率 | 效果（实测同一首歌、同样段数上限） |
|---|---|---|
| `fast` | 0.62× | 15 段，平均单条 4.65s |
| `balanced` | 1.00× | 14 段，平均单条 5.14s |
| `cinematic` | 1.60× | 13 段，平均单条 5.54s |

### 参数优先级

**命令行显式传参 > 已存偏好 > 内置默认值。**

为此 CLI 所有偏好类参数的默认值都是 `None`（而不是内置默认值）—— 否则分不清
"用户没写"和"用户写了恰好等于默认值"。`--no-prefs` 可整体跳过已存偏好。

画面类偏好会作为**每段的基础 effects** 传给渲染器，EDL 里逐段的 effects 可以覆盖它。

### 设计要点

- **只用标准库 `sqlite3`** —— 不为一个键值存储引入 ORM
- **读偏好永不抛错** —— 库损坏/读不到时回落默认值，存储问题不该让出片失败
- **写偏好严格校验** —— 非法值（画幅写 `cinema`、未知键、非数字）直接报错，
  不会污染数据库；校验失败时已存值保持不变
- **值统一按 JSON 存，读回按类型还原** —— `--set use_llm false` 得到的是
  Python `False` 而不是字符串 `"false"`
- `list_runs` 会列出未完成的运行，`stats` 只统计已完成的

> `max_clips` 是**最终段数**的硬上限（不是候选池大小）。设小之后音乐尾部会没有
> 画面 —— 这是有意的：额度按时间顺序耗尽，**空隙只出现在尾部，不会留在中间**；
> 而且单条镜头不会为了填补空白而无限变长（实测修之前出现过一条 111 秒的镜头）。
> 结尾留白会在 `edl.json` 的 `meta.notes` 里写明。

## 用户画像（从对话推断的偏好）

除了用户手写的显式偏好，系统还能**从对话内容推断**稳定的使用倾向。

两者的区别很重要：

| | 显式偏好 `preferences` | 用户画像 `user_profile` |
|---|---|---|
| 来源 | 用户 `--set` 或直接指令 | 从对话/行为推断 |
| 性质 | 行为开关，**直接改变出片** | 带可信度的倾向，**只进提示词** |
| 出错时 | 用户自己设的，责任清晰 | 可能推断错，所以绝不自动改行为 |

> 为什么分开：推断一定会有错。如果推断直接写进行为开关，用户会发现"我什么都没设，
> 它却自己改了画幅"——那比不推断更糟。画像只作为上下文喂给 LLM，用户随时能看到、
> 能推翻。

### 用起来是什么样

```bash
python -m cs2clipper.pipeline --show-profile      # 看推断出的画像
python -m cs2clipper.pipeline --show-evidence 20  # 看支撑画像的证据（含原话）
python -m cs2clipper.pipeline --rebuild-profile   # 由证据重新汇总
python -m cs2clipper.pipeline --forget workflow   # 删掉某个维度（可多个）
python -m cs2clipper.pipeline --forget            # 清空全部画像

# 手工补一条证据（带依据，便于回溯）
python -m cs2clipper.pipeline --observe pacing cinematic "他说不要剪太快，要有余韵"
```

### 证据的四种来源与权重

| 来源 | 权重 | 含义 |
|---|---|---|
| `explicit_set` | 1.00 | 用户明确下达的指令 |
| `conversation` | 0.90 | 对话里明确说出的偏好 |
| `accepted_advice` | 0.70 | **用户认可了助手提出的方向/取舍** |
| `run_history` | 0.55 | 从实际出片参数推断 |
| `assistant_inference` | 0.45 | 助手从行为模式推断（最弱） |

`accepted_advice` 这一类是关键补充：很多偏好是通过"用户同意了助手的建议"体现的
（例如接受"运动模糊太贵所以默认关闭"），这些话里并**不含偏好关键词**，但确实是
偏好证据。所以推断引擎会成对处理"助手建议 → 用户接受"。

### 置信度怎么算

```
confidence = (胜出权重 / 总权重) × min(胜出权重 / 0.7, 1.0) × 证据数量天花板
```

两处都踩过坑：

- **饱和度分母**最初设成 `3.0`（要求"权重累到 3 才算证据充分"），结果用户明确下达的
  指令也只得到 0.3 分——恰好卡在进提示词的阈值上，**一条结论都进不去**，功能形同虚设。
  显式诉求本来就该一次就够，`0.7` 才是合理门槛。
- 改完后单条证据又直接给到 `1.0`（等于完全确定），同样不对。所以加了证据数量天花板：
  **一条证据最高 0.85**，多条同向证据才趋近 1.0。

### 画像如何影响出片

`profile_brief()` 会把可信度 ≥0.3 的结论转成中文描述，作为 `user_profile` 段注入
LLM 提示词：

```json
"user_profile": {
  "camera": "要跟拍高光人物（不要俯瞰全图）",
  "motion_fx": "不要运动模糊",
  "tech_stack": "偏好本地 sqlite 存储，不要外部依赖",
  "workflow": "暂不处理版本控制，先做功能"
}
```

系统提示词里区分了两者的效力：`user_preferences` **严格遵守**，`user_profile`
**用作口味参考**。

## 自检

项目自带一套完整自检（`cs2clipper/selftest.py`），按模块分组、每项独立捕获异常，
一次运行就能定位"哪个模块坏了"，而不是第一个报错就中断。

```bash
# 单元 + 集成（约 3 分钟，不需要 API key；Web 那组会真起 uvicorn 并出一次片）
.venv\Scripts\python.exe -m cs2clipper.selftest

# 跳过 Web 那组（更快）
.venv\Scripts\python.exe -m cs2clipper.selftest --no-web

# 加端到端出片（真实渲染，较慢）
.venv\Scripts\python.exe -m cs2clipper.selftest --e2e ^
    --music "D:\CloudMusic\xxx.mp3" --aspects wide,tall

# 额外验证 LLM 编排
.venv\Scripts\python.exe -m cs2clipper.selftest --e2e --llm
```

另外 `tools/dev/` 下有**取证用**脚本（不是自检的一部分，需要真数据）：

| 脚本 | 用途 |
|---|---|
| `lint.py` | 自写的 AST 静态检查（未使用变量/导入、`except: pass`、超长函数）；本机 pip 源上没有 ruff/pyflakes |
| `repro_review.py` | 复现时间轴偏移、`_extract_json` 返回 list、补齐镜头声明时长超源等缺陷 |
| `check_music_real.py` | 在真实歌曲上核验 `has_climax` / `curve_hz` / `beats_per_second` / 段内 BPM |
| `check_web.py` | 起真服务把 31 个 Web 端点全打一遍（自检里的 Web 组是它的精简版） |
| `check_frontend.py` | 前端静态一致性：JS 的 id/class 选择器、接口路径、语法（无浏览器时的替代验证） |

覆盖范围：

| 分组 | 项数 | 关键检查 |
|---|---|---|
| 环境 | 5 | ffmpeg/ffprobe 可用、目录可写、模块可导入 |

## 画面与性能优化（P0–P4）

按优先级实施的四项优化，均已通过自检并有实测数据。

### P0 逐段动态镜头（跟拍）

原先全片共用一个视口（跨度约 3158 units ≈ 整张 dust2），单人高光镜头里主角只是
地图上一个点，观众感受不到"这一枪打得好"。现在**每段按该段的参与者重新取景**。

关键设计是**只框住本段的参与者，不是全场 10 人**：

> 实测过用全场玩家算取景：到中心的 95 分位距离达 1995~6484 units，所需跨度
> 4000~13000 —— 40 条素材里 39 条撞上跨度上限，跟拍完全退化成"永远最远"，
> 等于没做。原因很直接：素材讲的是**一个人的高光**，而地图另一头的队友会把
> 包围圈撑到整张地图。

所以 focus 取 `{主角} ∪ {受害者} ∪ {助攻者}`，并用**位置中位数**当镜头中心
（包围盒会被单个绕后的玩家拽偏）。效果：

| | 跨度 |
|---|---|
| 全片统一（旧） | 3158 units |
| 逐段跟拍（新） | 中位 **1329** units，范围 700~2600 |

另外 `zoom = 1.0 + 0.45 × arousal` —— 越激烈的段落镜头越近，观众能看清交火。

还有一处必须处理的细节：主角跑到画面边缘时，它的**名字标注会被画面边界切掉**
（圆点还在画面内、文字已经被切）。所以取景会把主角约束在画面内并留 20% 边距
（试过 12%，不够）。

### P4 画面质感

| 效果 | 状态 | 代价 |
|---|---|---|
| 段首尾淡入淡出 | **默认开启** | 仅首尾若干帧做 `Image.blend`，中段直接跳过判定 |
| 击杀瞬间震屏 | **默认开启** | 地图区整体平移几像素，约 2% |
| 拖尾运动模糊 | **默认关闭**（可开） | 约占单帧预算 30~45% |

运动模糊之所以默认关闭，是因为 PIL 没有小范围模糊原语——全帧高斯在 1080² 下要
19~28ms，把渲染从 25fps 拖到 10fps；而且 2D 雷达上玩家是匀速平移，模糊的观感
提升有限。想开启就把 `RenderStyle.trail_blur` 设为 1.5~2.5，但要接受渲染翻倍。

淡入淡出对"软化硬切"很有效（换回合时场景跳变最刺眼），而且几乎没有成本，所以
无需 ffmpeg 的 `xfade` 就解决了硬切问题。

### P1 渲染提速：实测 1.64x

按 cProfile 定位的热点逐项优化：

| 优化 | 说明 |
|---|---|
| 暗角烘焙进底图 | 原先每帧对整幅图 `Image.composite`，占单帧 22% |
| 底图预转 RGBA | 原先每帧 `convert("RGBA")`，1080² 约 8ms/帧，纯浪费 |
| 每帧下标缓存 | trails/players/kills 三层各自 `searchsorted`（每帧 57 次），改为算一次复用 |
| 击杀坐标预计算 | 击杀位置只取决于击杀 tick，与当前帧无关，移到逐帧循环外 |
| 轨迹改降采样折线 | 原先每帧每玩家画约 96 段线，改为抽稀后单条 polyline |

交错多次采样的中位数结果：

| 配置 | fps | 相对 |
|---|---|---|
| 优化前 | 13.4 | 1.00x |
| **优化后（当前默认）** | **21.9** | **1.64x** |

127 秒的歌预计渲染 **4.74 分钟 → 2.90 分钟**。

## 常见问题

**成片比音乐短 / 结尾没画面？**
看 `edl.json` 的 `meta.coverage_warning`。正常情况已被 `_top_up_tail` 自动修复；
如果素材池太小（`--max-cards` 调太小），可能补不满，此时调大 `--max-cards`。

**LLM 编排不可用？**
会自动回落到确定性编排（`meta.planner` 会写成 `fallback(llm_error)`），
成片照样能出。也可以直接用 `--no-llm`。

**想改剪辑风格？**
- 改镜头松紧：`planner._segment_limits()` 里的 `lo/hi`（最短/最长单条时长）
- 改画面观感：`radar.RenderStyle`（`dot_world` 圆点大小、`trail_len` 拖尾长度、
  `show_places`/`vignette` 等）；也能通过 EDL 每段的 `effects` 字段单独覆盖
- 改评分偏好：`demo.py` 顶部的 `SCORE_*` 常量

## 当前限制

- **转场仍是硬切**，但已用**渲染器内的段首尾淡入淡出**软化（P4），不再是问题。
  接 ffmpeg `xfade` 反而需要重算时间轴（xfade 吃掉重叠时长），收益有限。
- **画面是 2D 雷达，不是游戏画面。** 需要真实 3D 画面得走 HLAE + 游戏内录制，那是另一条路线。
- **取景在段内是固定的**（不随镜头推移）。每段重新取景已经是相对旧版的质变；
  段内连续推拉会让观众晕，也不符合雷达图的观看习惯，暂不做。
- `demo.py` 里 `is_clutch` 已重写为 `find_clutch()`, 判定严格按定义:**主角成为自己
  队里最后一人、独自面对 >=2 敌人、并赢下回合**, 且他必须在残局窗口内有击杀。
  判定所需的两项事实都取自逐 tick 表: 每回合完整名单 (玩家会换边, 必须按回合建)
  与回合末血量 (判断谁真正活着 —— 不能用"没出现在死亡事件里"代替)。

  幸存者口径: `health > 0` **且** `is_alive`。审查时实测这份 24 回合 demo 里有
  1 个回合两个字段互相矛盾 (`health>0` 得 4 人 / `is_alive` 得 3 人), 所以取交集
  —— 多算一个幸存者会把"赢方恰好剩 1 人"顶掉而静默漏判, 少算最多漏一次残局。
  矛盾次数记在 `analyze_demo()["roster_stats"]["hp_alive_conflicts"]` 里。

  第一份 demo (g161-20260827...) 确实**一个残局都没有**, 旧实现判出的 1 个是
  名单/幸存者数据出错造成的假阳性。第二份 demo (g161-n-20260912...) 有 **5 个**
  真残局 (R8 1v3 / R9 1v2 / R12 1v2 / R20 1v2 / R22 1v3), 标签与 +80 加分都已验证。
  卡片上新增 `clutch_enemies` 字段 (1vX 的 X), 旧实现把这个信息完全丢掉了。

  注意: 残局判定需要逐 tick 数据, 因此 `analyze_demo` 必须用 `with_ticks=True`。
  名单构建失败时不再静默返回空字典 (`build_roster.last_error` 会上报到
  `analyze_demo()["roster_error"]`), 否则"所有残局消失"和"这局真没残局"无法区分。
- 运动模糊默认关闭（代价见 P4）。

## 真实音乐验证记录

用本机 `D:\CloudMusic` 的三首真实歌曲验证音频分析（合成测试曲掩盖了下面这些问题）：

| 歌曲 | 时长 | BPM | 段落数 | 判定 |
|---|---|---|---|---|
| chen陌懿 - 陪我过个冬DJ | 155s | 136.0 | 13 | drop 落在 122.3s（尾部高潮） |
| 在虚无中永存 - 英雄主义 | 127s | 117.5 | 11 | drop 落在 50.6s |
| 饺子WTF - 苦海无涯 | 238s | 99.4 | 16 | drop 落在 209.5s |

真实音乐暴露并已修复的**三个算法缺陷**：

1. **凭空编造高潮段。** 旧逻辑硬编码"能量排名第 0 的段 = drop"。而《英雄主义》
   全曲 RMS 只在 0.07~0.13 之间（几乎没有动态），首段因为微弱领先就被判成
   "高潮爆发段"。现在改为基于**峰值显著度**判定（`music.energy_stats`）：
   峰值段必须比全曲中位响 >=24%（硬下限 `PEAK_FLOOR`），且满足以下任一：
   比中位响 >=25%、比次高段响 >=15%、中段位差 (P90-P10)/median >= 0.35。

   这里踩过一次量纲错配：第一版判据是 `(max-min)/median < 0.35`，分子取了
   **含最安静段**的极差，而末段淡出 (RMS 0.0084) 会把这个无量纲比值撑到
   **1.138** —— 于是"全曲无明显高潮"的歌照样被判 has_climax=True、照样产出
   drop，保护从未在真实歌曲上触发过（实测三首歌 1.138 / 0.739 / 0.986，
   全部 >= 0.35，`planner` 的"无高潮"分支是死代码）。现在 `dynamic_range`
   只用于展示，判定只认无量纲的峰值比值。

   修复后在三首真实歌曲上的实测结果（`tools/dev/check_music_real.py`）：

   | 歌曲 | peak/median | peak/次高 | prominence | 旧判据 | 新判定 | drop |
   |---|---|---|---|---|---|---|
   | 英雄主义 127s | 1.2605 | 1.0255 | 0.5593 | True | **True** | 50.6s（与旧版一致） |
   | 陪我过个冬DJ 155s | 1.2150 | 1.0112 | 0.6169 | True | **False** | 无 |
   | 苦海无涯 238s | 1.1192 | 1.0000 | 0.2559 | True | **False** | 无 |

   三首歌的**段级原始 RMS 相对中位**（降序）说明为什么这样判：

   * 英雄主义 `[1.26, 1.23, 1.14, 1.10, 1.09, 1.00, …, 0.67, 0.08]` —— 最高段确实
     比中位高 26%，有一个真实的安静收尾，判有高潮。
   * 陪我过个冬DJ `[1.22, 1.20, 1.18, 1.17, 1.06, 1.03, 1.00, …, 0.51, 0.46]` ——
     峰值只比中位高 21.5%，前四段几乎并列（1.22/1.20/1.18/1.17），是**平台**不是
     落差；离 1.24 硬下限差 2%，判无高潮（比旧版的"122.3s 有 drop"更保守）。
   * 苦海无涯 `[1.12, 1.12, 1.11, 1.09, 1.08, 1.03, …, 0.19]` —— 最高两段几乎持平
     （peak/次高 = 1.000），整首一路缓降，**没有落差**。旧判据的 0.94 完全是
     末尾那个 0.19 的安静段撑出来的。

   判定"无高潮"并不会让编排变温吞：`planner._pick_segment_limits` 会在
   `has_climax=False` 时把**相对最激烈的那几段**当高光段处理（用歌自己的动态走），
   这条分支以前是死代码，现在真的会被走到。

   ⚠️ **阈值鲁棒性仍未解决**：英雄主义的 peak/median = 1.2605，离 1.24 硬下限只有
   1.6% 的余量 —— 换一版 librosa、换一次分段边界就可能翻转结论。`energy_stats`
   现在会输出 `peak_margin` 把这个余量直接报出来。量纲错配是确证并已修的缺陷，
   但阈值需要用更多真实歌曲重新标定。

2. **情绪标签自相矛盾。** 旧版在"高激烈度 + 暗"时输出"沉重压迫"，而全曲最激烈的
   段落同时又是"被压迫的"。现在用 `rel_energy`（相对全曲中位的能量）消歧：
   偏响的暗色段是"厚重有力"，偏轻的才是"压制感强"。

3. **段落边界与节拍无关。** 旧版边界完全由能量变化率决定，剪辑点落在拍与拍之间。
   现在边界吸附到最近拍点（`beat_frames`），段落起点即重音位置。

另外把目标段长从 20s 收紧到 12s —— 旧设定下真实歌曲会出现 48~64 秒的超长段落，
一段里其实包含好几个情绪层次，对剪辑没有参考价值。

### 完整测试中又发现的一个缺陷

LLM 编排路径出现**节奏倒挂**：高激烈段的镜头平均 **10.41s**，其余段落 7.66s
（比值 1.24）—— 最激烈的段落反而镜头最长，与音乐完全相反。

根因有两层：

1. LLM 常给高激烈段只排 1~2 条镜头，`_expand` 为了铺满段落时长只能把它们
   拉长（分配器的 `hi` 上限被"必须填满"压过）。
2. 修这个问题的 `_split_overlong_clips` 原先**只返回说明字符串，拆分结果被丢弃**，
   调用方写成 `notes = _split(...)` 等于什么都没做。这类 bug 不报错、只让成片变难看。

修完后 LLM 路径比值 **1.24 → 0.76**，段数 14 → 28，两条路径的节奏都与音乐一致。

### 已知未确证的疑点

- `energy_stats` 的四个阈值（1.25 / 1.15 / 0.35 / 硬下限 1.20）是在**三首**真实歌曲
  上标定的，其中两首（英雄主义、陪我过个冬DJ）的 peak/median 只有 1.2605 / 1.2150，
  离硬下限 1.20 的余量分别只有 5% 与 1.3%。量纲错误是确证的，阈值本身仍偏紧，
  需要用更多真实歌曲重新标定（见上表下的说明）。
- `music._norm` 的 5/95 百分位裁剪在**极度偏斜**的分布上会退化：实测"97% 帧安静 +
  3% 帧响"的信号里 P5 与 P95 落在同一侧，归一化后整条曲线恒为 0（情绪轴全平）。
  真实音乐上没复现过，暂不修。

## Web 界面

```bash
.venv\Scripts\python.exe -m cs2clipper.webapp                 # 默认 127.0.0.1:8760, 自动开浏览器
.venv\Scripts\python.exe -m cs2clipper.webapp --port 9000 --no-browser
```

界面分四页：

| 页 | 内容 |
|---|---|
| **出片** | 选音乐（可浏览任意盘的目录树）/ 选 demo（自动扫工作区与常见下载目录）→ 参数（画幅/帧率/段数/节奏/编排方式/输出目录）→ 一键出片。带**六阶段实时进度条 + 日志流**，可中途停止（在下一段渲染前中止，已完成的片段照样出片）|
| **成片与时间轴** | 内嵌播放器（支持拖动进度，因为走 `FileResponse` 的 Range）+ 下载 + **EDL 时间轴**（每格一段，颜色深浅 = 所在音乐段落的激烈度）+ 音乐段落表 + 素材卡片表（回合/玩家/评分/标签/残局敌人数） |
| **偏好与画像** | 18 项偏好读写（改动高亮、一键清空）+ 用户画像（置信度条 + 依据原话）+ 手工补证据 |
| **历史记录** | 运行记录表 + 汇总统计（次数/镜头数/平均耗时/成片总量/数据库大小）+ 单次运行的逐段明细（玩家、回合、评分、标签）|

技术选型：**Starlette + uvicorn + 原生 JS**，零新增依赖 —— 本机 pip 源上没有
fastapi/flask，而 starlette/uvicorn 是 langchain/mcp 的既有依赖，已经在环境里。
前端是一个 HTML + 一个 CSS + 一个 JS，**没有构建链**（本机也没有 node/npm），
改完刷新即可生效。

进度通道：`cs2clipper/progress.py` 是一个约 200 行的极薄事件层，`pipeline.run(on_event=...)`
会把六个阶段的结构化事件推给回调，Web 端用 SSE 转发给浏览器。三个刻意的设计：

1. **回调抛异常绝不影响出片** —— 进度只是附加信息，不该因为一个 UI 的 bug
   丢掉一次 200 秒的渲染（有断言）。
2. **百分比单调** —— `analyze_music` 与 `analyze_demo` 在图里是并行节点，事件会
   交错到达；各自按权重算出来的百分比实测出现过 `8.0 → 0.0 → 30.0`（进度条倒退）。
   `Bus` 统一取历史最高值。
3. **`log` 事件不推进度条** —— 它可能在任何时刻从任何阶段打出来（例如 plan 阶段的
   告警在音乐还没分析完时就发了），只把它当文本流。

安全边界（本地工具，但默认只监听 `127.0.0.1`）：素材路径允许任意盘（音乐库常在
别的盘）但必须是存在的常规文件；**产物路径只允许工作区内**，由 `media.safe_under`
做 realpath 前缀校验（`../../../.env` 会被 403）；同一时刻只跑一个渲染任务，其余排队。

没有浏览器时的验证：`tools/dev/check_frontend.py` 静态检查 JS 里的 id/class 选择器
与接口路径是否真实存在（这类错误在浏览器里表现为整个界面卡死，而后端日志一个字
都没有），`tools/dev/check_web.py` 则起真服务把 31 个端点全打一遍。
